# YAIC: результат MQTT вместе со снимком

## Цель и согласованное направление

Пользователь выбрал один MQTT JSON с результатом и image_b64, чтобы будущий
MQTT → Telegram сервис не сопоставлял изображения и результаты из разных потоков.
Сейчас запрошен только план доработки YAIC. Реализация, бот и деплой не входят
в этот этап. Частные сведения о развёртывании в документы проекта не включать.

## Подходы

- Два потока с event_id требуют хранения и сопоставления на стороне доставки.
- URL изображения требует отдельного хранилища, срока жизни и доступа.
- Один JSON с image_b64 — выбранное пользователем направление: самодостаточное
  сообщение, но изображение занимает примерно на треть больше места.

## Контракт

В MQTT_TOPIC_OUT публикуется существующий JSON плюс image_b64 — стандартный
base64 без data-URL префикса. После декодирования это точно те байты из
ProcessingResult.image_bytes, которые получил классификатор. Нет повторной
загрузки URL, перекодирования, уменьшения или выбора другого кадра.

Все прежние поля, включая source, device, event_id и person, сохраняются.
Отсутствующий входной event_id не создаётся искусственно. Изображение добавляется
ко всем успешным результатам, включая случаи без людей. Фильтрация людей,
подавление повторов и отправка уведомлений принадлежат будущему сервису.

Изменение ограничено MQTT-сериализацией: Processor.payload и JSONL автономных
команд остаются прежними. Это инженерное предложение для сохранения совместимости
CLI и минимального изменения кода. ProcessingResult уже содержит байты снимка.

Публикация результата: текущий настроенный топик, QoS 1, явно retain=False.
QoS 1 допускает дубликаты; отсутствие retain не гарантирует отсутствие очереди
старых сообщений у постоянных MQTT-сессий. Строгие JSON-потребители и лимиты
брокера должны быть проверены до развёртывания.

## Размер и ошибки — предлагаемые инженерные решения

Добавить MQTT_MAX_OUTPUT_BYTES: положительное целое, по умолчанию 16777216
(16 MiB), ограничивает UTF-8 размер сериализованного JSON. Это локальный предел
приложения, не утверждение о настройках действующего брокера. До деплоя сверить
лимит с брокером, учитывая заголовки MQTT, имя топика и возможности подписчиков.

При превышении лимита не отправлять ни неполный результат, ни JSON без фото:
журналировать source и размеры без изображения, выставлять operation=error.
Успешный результат не должен терять фото незаметно для потребителя.
Проверять немедленный код возврата publish; при ошибке — operation=error,
без idle. Не блокировать callback ожиданием PUBACK; idle означает окончание
обработки/принятие публикации клиентом, а не доставку подписчику.

## Проверка

Точное совпадение байтов для binary/base64/URL входов; сохранение метаданных;
разделение камер; один результат без retain; границы размера и ошибка publish;
неизменный JSONL CLI. Никаких изображений/base64 в логах или MQTT_TOPIC_LOG.
Полный pytest плюс изолированный MQTT smoke-test с синтетическим VLM до деплоя.
Реальная камера, получение свежих Tuya-снимков и уведомления — отдельные этапы.
